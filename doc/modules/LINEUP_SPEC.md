# Lineup 阵容方案

Status: Implemented; real game acceptance pending
ContractVersion: 1
OwnerPaths: `analysis/AolaLoader/Features/Lineup/**`, `analysis/AolaLoader/UI/Lineup/**`

## 职责和入口

“扩展 → 阵容方案”提供读取当前背包、保存为 JSON、打开 JSON、恢复阵容及停止。
恢复账号内原亚比实例及顺序、魂卡、魂器和已绑定晶钥。装备、技能、培养属性、皮肤不参与保存或恢复。
魂器只穿戴；方案空槽跳过，不卸下当前额外魂器。默认保存目录为
`%LOCALAPPDATA%/AolaLoader/Lineups`，也可选择其他位置。

名称优先使用分发目录中的 `Resources/BattleAssistant/catalog.json`，缺项显示编号；
运行时不依赖整理表或反编译目录。方案由用户选择读取/保存，不自动修改现有方案。

## JSON 契约

独立文件，不接入 theme/petMorph/battle Section，camelCase 字段：
- schemaVersion=1、name、savedAt、ownerPlayerId、pets。
- pets 为 1 至 6 个条目，数组顺序即背包顺序；条目包含 petId、raceId、name。
- soulCards 为五个非负编号，0 表示目标空槽；null 表示不参与恢复。
- soulArtifacts 为两个槽位，各项为 {instanceId,configId} 或 null；空项跳过。整个字段 null 表示不参与恢复。
- crystalKeys 为两个非负编号或 null。目标槽为 0、当前非 0 时，预检拒绝，不猜测卸下接口。

文件上限 1 MiB，拒绝重复 JSON 字段、不支持的版本、未知字段、非整数编号、重复亚比和重复分配魂器实例。
UTF-8 无 BOM，同目录临时文件原子替换，失败保留旧文件。不含登录凭据、SID、序号或任意待执行命令。
方案固定所属玩家及亚比实例，种族编号仅核对身份。恢复魂器实例，不改写词条。

## 读取

LineupCoordinator.ReadAsync 创建短生命周期 LineupSession，先订阅 PacketHost，再通过 IAolaCommandSender
发送 id=13/1212。从 2212.pms 取顺序，按 `LineupPetParser.View` 选择的 pmPView/pmSView.i 关联；解析 pcp.soc/tt/ctk。
不存在的类别保留 null，不伪造空槽；资料无效则失败。
随后再次 1212 → 2212 对照完整阵容，不再额外逐只查询详情。
读取期间变化、资料缺失或身份不一致，不更新窗口中已有有效方案。

## 恢复

1. 读取背包核对账号，逐只读取目标实例，核对种族和配置适用性。
2. 需要切换晶钥时用 ACK241227_1 查询绑定编号；需要清空或首次绑定则在修改前拒绝。
3. 有目标魂器时用 ATT231229_0 查询持有资料，以结构化条目的 ui/ti 核对实例及配置编号；缺项或无法识别则停止。
4. 名单不同则提交 id=13/1222 {pms}，核对 2222.pms 和新的完整背包。
5. 每只重新读取现状。魂卡差异执行 ASC221104_40 {petId,ids}，收到查找资料后执行
   ASC221104_2 {petId,ids,bk:0,tf:true}。不用 _41 推算空闲库存，不先全部卸下。
6. 魂器非空目标槽不同则执行 ATT231229_1 {petId,ui}；晶钥差异执行 ACK241227_3 {petId,slotId,id}。
   三类配置均使用扩展 42。已一致的项跳过。
7. 每项穿戴必须返回整数 r=1，随后读取单只亚比核对配置；末尾再读整个背包，
   核对顺序及全部参与恢复字段，只有最终一致才报告成功。

魂卡 _40 不是穿戴成功回执：有 r 时要求整数 1，没有 r 时至少存在除 _cmd 外的资料字段，拒绝空响应。
查找资料不用于推断库存或改写用户提供的 tf=true 流程；
穿戴成功以 _2 回执及 2211 回读为准。新的查找/持有查询响应仍待用户实际运行确认。

## 依赖、线程和生命周期

CompositionRoot 构造协调器，窗口经 ChildWindowCoordinator 复用。模块只依赖 ActiveSend、PacketHost、
只读 Battle state 契约，不访问 CefSharp、静态 IPC 或原始 socket。不新增 SWF 补丁或第二连接。

同一协调器同时只运行一个任务。每个请求先登记参数，再调用发送器；
匹配发送抓包后才接收同进程、同 socket 响应。响应等待上限为提交返回后 15 秒，不盲等固定间隔连续发包。
首次背包资料和后续消息固定账号；进入战斗、重新登录、连接变化或额外同类/配置操作时停止。
运行前检查已知战斗状态。

后台进度使用 BeginInvoke，窗口关闭/Dispose 取消任务；Session 在结束时退订。
停止只取消后续操作，已提交命令可能继续生效；失败保留进度，不自动重发或回滚。
再次恢复重新读取现状，仅执行剩余差异。

## 验证边界

按用户要求不新增或运行子模块自测、冒烟、日志回放和真实游戏验证；仅编译供用户验收。
运行时输入检查和服务器回读属于功能必需逻辑，保留。

同名服务端响应没有宿主 requestId，发送抓包、串行等待和最终回读用于降低混淆。
执行时请勿同时进行手动换宠/配置或其他发包。
魂器查询无法识别、魂卡查找返回空数据、服务器拒绝或回读不一致都会停止，需要按真实反馈补充。
编译成功不代表游戏内验收。

用户验收：保存方案后手动变更阵容和配置，再从 JSON 恢复，核对顺序及三类目标配置、
空魂器跳过、停止/失败提示和后续正常游戏操作。不得执行装备更换、魂器卸下或晶钥首次绑定。

## 2026-09-10 读取超时修正

用户提供的 `data/battle/_0910-1700.json` 中，1212 正常返回完整六只配置；
随后五次 1211 在约 181 毫秒内提交，前四次有 2211，最后请求亚比 3021 后样本中未见响应。
该证据不能单独证明服务器限频，但显示保存流程存在多余的密集查询。

读取保存改为两次 1212/2212 完整快照对照，去掉逐只 1211 复核；
恢复保留必要的单只查询。Session 按上次匹配发送抓包计时，相邻请求至少间隔
500 毫秒，同时仍等待真实响应，不自动重发。500 毫秒是本模块的保守发送节奏，
不是已确认的服务器限频阈值。超时信息区分未匹配到发送和已发送未匹配到响应，
并附带目标亚比编号。修正仅编译，实机验收仍由用户完成。
